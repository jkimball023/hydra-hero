How Hydra works

Agents do the work. You control the system.

Scroll to follow one issue through a workflow defined once.

An issue arrives from Slack — "add rate limiting to the api"; it could as easily come from the web dashboard or the CLI. Hydra maps the work onto shared context — standards, repo, docs, history — using a workflow defined once, and starts agent sessions in parallel. Claude finds the cause, an N+1 query, and hands off to Codex, which patches it. Mid-run, a Jira status change wakes the pm agent, which takes over the docs lane from Copilot, alerts James in Slack, and runs its own parallel path drafting release notes that land in shared context at the merge. A replay of the same issue with a different prompt races the main run on a second path; when it stalls, Jayantk takes the session over interactively, and a compare node merges the paths — variant A is kept, your judgment. A "your turn" marker appears on the Claude lane: input is available but optional, and the fleet continues without it. The work converges into pull request 1284 on GitHub, where lint, tests and build pass. The run waits at review for your call: agents do the work, you decide what ships. On approval it merges to main; the merge wakes the security agent and alerts the security-review channel, and the result is written back into shared context, so the next run starts smarter.
